## Left in this changeset

- `dashboard/dashboard.go:679-681` and `:1030-1032`: the three search fields `searchTyping`, `searchInput` and `searchTerm` now exist on both `detailView` and `QueueDashboard`. The logic that uses them is also in two copies:
  - `detailView.openSearch`, `closeSearch` and `activeQuery`, next to the dashboard's own `activeQuery` and its `updateSearchTyping` Enter/Esc branches.
  - `updateDetailSearchTyping` (`:2549`), next to `updateSearchTyping` (`:2522`).

  Three fields that always travel together are a type waiting to be born. A small `searchState` type would let both views share one Enter/Esc/typing state machine. Its methods would be `open`, `close(term)`, `query()` and `handle(key) (applied bool)`. This changeset created the second copy. I did not fix it: the tests read `m.searchTerm`, `m.searchInput` and `m.detail.searchTerm` directly (for example in `dashboard_detail_search_test.go`), so the extraction would change test files. Under the standard, that makes it more than a reversible in-place fix.
- `dashboard/dashboard.go:4145` `detailEmptySearchLine` uses the same format string as `emptySearchLine` (`:3897`), with the noun passed as an argument. That is two copies, which is under the Rule of Three, so I noted it here only. If a third surface searches, `emptySearchLine` should call `detailEmptySearchLine(m.page.searchNoun, query)`.

## Revealed by this changeset

- `updateDetailView` (`dashboard.go:2190` onward) gives keys to the item menu, then the container menu, then search typing, then the peek, then the list. It does this with a chain of `if` statements, and each one resets `pendingG`. The new `m.menu` and `searchTyping` branches had to be placed carefully in that chain, because `update` reaches the detail before the menu. The refactoring it wants: one ordered list of "who owns the keyboard now" handlers (one keyboard owner per modal layer), used by both `update` and `updateDetailView`. Then a new overlay is one entry in the list, not a new place to edit in two dispatchers.
