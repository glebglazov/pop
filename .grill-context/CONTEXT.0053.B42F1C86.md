+ Derivation stamp
  The fingerprint of the build that computed a cached answer — the running executable's path, size and mtime, plus the injected build version — mixed into every **Cache database** key ahead of the answer's own inputs (ADR-0265). It is the same `{size, mtime}` fingerprint the **Manifest memo**'s content key already applies to every file in a set folder, applied to the last input that was missing: the binary whose rules turn those files into a verdict. Resolved once per process and held, so a daemon and a freshly installed CLI occupy different stamps and neither serves rows the other's rules produced; a stamp that cannot be resolved becomes a per-process random value, which misses everything.
  avoid: cache version, derivation version (nothing is hand-bumped), schema version (that is the store's), build id

~ Manifest memo
  The memoization of a Task set's manifest load and validation, keyed on the **Derivation stamp** plus the set directory's content — `index.json`'s bytes plus every task markdown's mtime and size plus the directory's name set, because an unlisted `.md` flips the set to MALFORMED through the orphan check. Load and validation are a pure function of those files *and of the validating build's rules* (no store, no git, no config, no clock), which is why the stamp is in the key at all: without it a rule change with no file change served the old verdict forever (ADR-0265). It wraps `LoadManifest` itself, below the impure refresh that calls it, so every surface that walks the same definition path serves from one answer: the three passes `pop work status` makes over a repo group, both **Work dashboard** pages, and each 2s poll after the first. Unlike the **Git fact memo** its lifetime spans loads — that is the point, since a poll that re-validates unchanged manifests pays the open cost again. It has two tiers (ADR-0243): a process-lifetime LRU, which is why it is bounded at all, since the **Work supervisor** holds it for the life of the daemon; and beneath it one row per set directory in the machine-local cache database (`cache.db`), which is what stops a fresh process re-reading every task markdown on the machine to re-derive what the last one already derived. Both tiers are consulted under the same freshly computed key, so a persisted entry is no more authoritative than an in-memory one, and a cache failure at any point is a miss. The **Work supervisor** writes the persisted tier as it ticks, so a dashboard or a CLI command usually opens onto work already done rather than only the second open — deliberately unlike its opt-out from the **Git fact memo**, because validation is a pure function of files and a tick's own writes move the content key honestly. It writes on a hit in its own tier too, at most once per key per cache handle: a daemon holding one process tier for days would otherwise offer a set to the cache exactly once, and deleting `cache.db` under it would leave every later open cold.
  avoid: manifest cache (it persists, but never authoritatively), set cache, warm cache

~ Cache database
  The machine-local SQLite database at `$XDG_CACHE_HOME/pop/cache.db` holding every derived answer pop may recompute rather than lose. It is not the **Execution state store**: nothing in it is authoritative, every entry is re-validated before it is served against both the source it was derived from and the **Derivation stamp** of the build that derived it (ADR-0265), and clearing it is always a valid repair — `pop cache clear`, or deleting the file, which stays supported under a running pop. Those properties are what earn it a home under the cache dir and a name general enough for its second table, and what separate it from the deleted glob cache, which was persistence with nothing to validate against.
  avoid: pop.db (that is the state store), warm cache, glob cache
