# Work rows interleave across kinds by creation date

On page A of the Work dashboard, every Map sorted below every Task set, under every preset. That was not the preset's doing: `work.BuildSnapshot` loads each kind in fixed precedence, sorts each kind's containers with that kind's own `Less`, and concatenates the blocks, so `Kind.Less` is *"never asked to compare across kinds"*. [ADR-0173](0173-work-is-one-kind-interface-with-data-shaped-returns-and-kind-side-adapters.md) chose that deliberately and priced it: *"an urgent Map can never outrank a `DONE` task set, and … a Map no longer interleaves between two projects' task sets the way the single comparator let it."* A preset declaring `created_desc` makes the price conspicuous rather than causing it — the Task-set block becomes a clean date list and the Maps hang off the bottom as an obviously out-of-sequence tail. Presets already treat Maps as first-class for *selection*, `created_within` included; ordering was the only place they were second-class.

The decision: **creation date is the cross-kind ordering key on every Work read surface, and kind precedence is demoted to a tiebreak of last resort.** `work.Container` gains a `CreatedAt`, stamped by each kind in its own `Load` exactly as the builder already stamps `Kind`, read from the `YYYY-MM-DD[-HHMM]` identifier prefix via the existing `tasks.IDCreatedAt` — no new persisted state and no lifecycle instants, keeping [ADR-0197](0197-work-view-presets-replace-the-inclusion-toggles.md) decision 4's rule. The whole comparator moves into `work`: membership tier, then `CreatedAt` descending, then kind precedence, then the owning kind's `Less` within a kind. `work` can compute the tiers itself because `LiveDrain`, `AutoDrain` and `Orphaned` already live on the shared `Container`, so a live drain still floats above everything and the seam still imports no kind. A **zero** `CreatedAt` means "no opinion": it sorts after every dated row and falls through to `Less`. That is how Routines opt out — page B is single-kind and ordered by Routine relevance tier, which a date key would scramble, and [ADR-0197](0197-work-view-presets-replace-the-inclusion-toggles.md) decision 10 already recorded that *"a Routine has no creation date."* It is also where a Map registered before this change with an undated id lands.

The ADR-0121 status scheme is not deleted, it is demoted from the implied default to an explicit opt-in: the preset `sort` field gains a third value, `status`, meaning exactly the ordering pop had before this change — kind-precedence partition, each kind's own comparator, Maps in a trailing block. Absent `sort` now means `created_desc`. That flip is the whole behavioural change: the shipped `active`, `unfolded`, `all` and `muted` presets declare no `sort` and so all become date-ordered, `recent-7d` and `recent-30d` already declared it. Nothing shipped pins `status`; it exists for whoever wants the old ranking back in one line.

Two rejected alternatives worth remembering. **Shared status facets** — a small cross-kind band set both kinds map onto, so the status scheme survives and Maps land in the right part of it — is the *"shared vocabulary in disguise"* ADR-0173 turned down, and the objection has not weakened: the facets would be defined by looking at two kinds and re-litigated by the third. **Letting kinds signal the mode by stamping `CreatedAt` only when their preset asks for date order** costs nothing to build and reuses the zero-means-no-opinion mechanism, but makes the page's ordering an emergent property of every kind independently agreeing — unenforceable across kinds, and one kind stamping when the others do not yields a silently half-interleaved page with no single place to look. The builder takes an explicit `work`-owned ordering enum instead, set at the CLI edge, so there is one authority.

## Consequences

- **Ordering is a builder parameter now.** `BuildSnapshotForPane` gains an ordering value (`OrderByCreated` | `OrderByKindPrecedence`); the CLI edge translates the active preset's `sort` into it. `work` stays free of a `config` import, which it has been so far.
- **`pop work daemon` pins `OrderByKindPrecedence` explicitly.** It builds single-kind snapshots, so nothing changes in practice, but its serial dispatch feeds the Checkout occupancy ledger where "first wins, rest defer" needs a defined order. Scheduling must not inherit a display default a config flip could move.
- **`pop work status` follows automatically** — it and the dashboard read one comparator by construction.
- **A Map id must carry the date prefix to register.** `<YYYY-MM-DD-slug>` was already the documented convention in the authoring guide pop itself prints, with no validator behind it. Once the prefix is the only thing ordering the page, an unvalidated convention is one hand-typed directory name away from silently dropping a Map to the bottom — the bug this ADR exists to fix. It becomes an entry in `mapRegistrationProblems`, printed with the rest of the fix list. The undated fallback stays for rows registered before the check.
- **The trade-off accepted:** a `DONE` set from yesterday now outranks a `BLOCKED` set from last week. What absorbs it is that the needs-you signal is carried elsewhere — the membership tiers survive untouched above the date key, and the preset roster selects by status rather than ordering by it.
- **Page header counts stay per kind.** `Kind.Summary` phrases joined in kind order, unchanged. A count is not an order, and "how many of each" becomes *more* useful once you can no longer read it off where the blocks start and stop.
- **Amends [ADR-0173](0173-work-is-one-kind-interface-with-data-shaped-returns-and-kind-side-adapters.md).** "Ordering is fixed kind precedence … then that kind's own `Less`" becomes "ordering is membership tier, then creation date, then kind precedence, then that kind's own `Less`". The no-shared-status-facets decision it defends is untouched — this ADR ranks across kinds on a key both already carry, not on a status vocabulary neither has.
- **Amends [ADR-0121](0121-work-supervision-read-surfaces-converge-hide-done-and-sort-by-status.md).** The status scheme stops being the default order and becomes the `sort: status` opt-in.
- **Amends [ADR-0197](0197-work-view-presets-replace-the-inclusion-toggles.md).** `sort` gains `status` as a third value; absent `sort` means `created_desc` rather than the status scheme. Decision 4's identifier-derived recency is reaffirmed and widened from a filter key to the ordering key.
- Glossary: **Work container creation date** is added; **Work surface sort order**, **Work view preset**, **Work kind** and **Work page** are redefined.
