# Dated identifiers are offered newest-first everywhere

Every surface that offers a Task set or a Map for a human to pick sorted them alphabetically, which for a `YYYY-MM-DD-slug` identifier means oldest-first — so the set made ten minutes ago sat at the bottom of the Tab list, under a year of finished work. [ADR-0080](0080-transfer-is-a-batch-recency-ordered-atomic-snapshot.md) already found this wrong for one verb and carved out `transfer export` as *"the single deliberate deviation from the otherwise-uniform alphabetical ordering"*. The carve-out was the right instinct scoped too small: recency is not what makes transfer special, it is what makes *picking* work at all, because the thing you want is nearly always the thing you just made.

The decision: **a dated identifier is offered newest-first on every surface that offers it for choice, and a sequence identifier is never reversed.** Dated identifiers are the `YYYY-MM-DD[-HHMM]-slug` names of Task sets and Maps; the ordering is a plain reverse lexicographic sort of the identifier string, shared by one helper in `tasks` that `wayfinder` imports. Sorting the folder name rather than the parsed date is deliberate: the prefix is fixed-width and leading, so the two agree, and the string sort needs no parsing, has no unparseable-id case to drop, and is one comparison that every surface can visibly be using. Sequence identifiers — the `NN-slug` task files inside a Task set and Decision tickets inside a Map — encode intended order of work rather than recency and stay ascending, so picking a container starts at the newest and walking its contents starts at the first.

Completion returns the ordering with cobra's `ShellCompDirectiveKeepOrder`, which is the half of this that actually reaches a human. Without it zsh's `_describe` re-sorts the candidate list alphabetically before drawing it, and bash ≥ 4.4 does the same absent `compopt -o nosort`; nothing in pop set the directive, which means ADR-0080's newest-first export ordering has almost certainly never been visible since the day it shipped. Sorting in Go without the directive is not a weaker version of this decision, it is a no-op.

## Considered options

- **Order by parsed date via `tasks.IDCreatedAt`** — rejected. It is the right key for the Work dashboard, which ranks a Map against a Task set and needs a real comparable instant, but here both operands are strings from the same namespace. Parsing buys nothing and adds an `ok=false` branch whose only honest handling is to drop rows from a picker.
- **Order by `RegIndex`** (the position a set holds in the registration list) — rejected. It answers "when was pop told about this", not "when was this made", and the two diverge exactly when an import or a re-register makes the question interesting. Two surfaces both claiming "newest first" off two different keys is a discrepancy nobody would catch and everybody would half-notice.
- **Reverse inside `ScanMaps`** so every Map consumer inherits it — rejected. A scan is a data source; giving it a display opinion hands the next consumer an ordering nobody chose for it. Three explicit reversals at the three read surfaces beat one invisible one.
- **Leave `pop tasks status` alone as display-only** — rejected, and it turned out not to be display-only at all (see below).

## Consequences

- **Amends [ADR-0080](0080-transfer-is-a-batch-recency-ordered-atomic-snapshot.md).** Its ordering clause is subsumed: export is no longer "alone among completion surfaces" in ordering newest-first, it is now unremarkable. The rest of that ADR — transfer as a batch, atomic, all-or-nothing snapshot — stands untouched.
- **`pop tasks status` keeps its partition and flips its tiebreak.** Missing first, then Done, then active by priority descending, exactly as before; what changes is that ties inside each group break newest-first instead of by registration order. The partition is the point of that table — it is how a human sees at a glance what is broken — and [ADR-0210](0210-work-rows-interleave-across-kinds-by-creation-date.md) made the same call one level up by keeping the membership tiers above the date key.
- **Priority still outranks recency.** A priority is a deliberate act; recency is a default, and a default must not override an explicit act.
- **The interactive picker moves with the table, deliberately.** `selectAutomaticTaskSet` walks the same rows and takes the first Ready one, so a bare `pop tasks implement` now starts the newest of two equal-priority Ready sets rather than the earliest-registered. Keeping the picker on the old order would have meant sorting a separate copy for display, and `pop tasks status` is documented as the thing you read top-to-bottom to know what runs next — a table that mispredicts `implement` is a worse failure than a tiebreak moving. Unattended supervisor dispatch is unaffected: `selectReadySets` re-sorts its own copy on unique `RegIndex`.
- **`pop tasks spend` gains completion.** It was the one task-set-taking verb with no `ValidArgsFunction`; a rule that holds "everywhere" cannot have a verb quietly outside it.
- **`pop map spawned`'s second positional follows.** It completes task sets from the other kind's store, so it inherits this without a special case — a cross-namespace consumer is still a picker.
- **`KeepOrder` makes pop's ordering load-bearing.** zsh's alphabetical pass has been masking any completion ordering bug pop has; with it off, a list built from unsorted Go map iteration would show visibly random order rather than being quietly rescued. That is an argument for the change, not against it — but it means an unsorted candidate list is now a visible defect. Stock macOS bash (3.2) ignores the directive and keeps alphabetical; no regression there, just no benefit.
- Glossary: **Newest-first identifier order** and **Sequence identifier** are added; **Task set priority**, **Next task** and **Status table** are redefined.
