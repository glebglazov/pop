# Pop resolves the terminal appearance itself, because glamour's auto style cannot

[ADR-0222](0222-markdown-documents-render-by-extension-through-glamour.md) decided that Markdown renders by extension through glamour, and added one clause in passing: "The renderer uses glamour's automatic style." That clause is wrong in the only environment pop runs in, and it is wrong in the worst way — silently, and always in the same direction.

`glamour.WithAutoStyle()` is `termenv.HasDarkBackground()` and nothing else (`glamour.go:306`). `termenv` refuses to ask the terminal whenever `TERM` starts with `tmux`, `screen` or `dumb` (`termenv_unix.go:233`, on the premise that "screen/tmux can't support OSC"), and its fallback for an unanswered background query is `ANSIColor(0)` — black. Black is dark. **Inside tmux, glamour's "automatic" style is therefore a constant that always says dark.** Pop is a tmux-native tool, so every pop user with a light terminal has been reading dark-palette Markdown on a light background: the Document peek, and `pop tasks artifacts --show` on a Review artifact.

The premise is also false. Measured in tmux 3.7 under Ghostty: a raw OSC 11 from a pane returns `rgb:fbfb/f1f1/c7c7`, while `termenv` reports `#000000` and `dark=true` in the same pane, with the OS appearance in either state. tmux answers; termenv never asks.

The decision: **pop resolves a Terminal appearance — light, dark or plain — and every palette it prints is selected from it. glamour is one consumer of that fact, not its owner.**

- **The answer is always the real background colour.** `charm.land/lipgloss/v2` queries OSC 11 with no `TERM` bailout, and pairs the query with DA1 in the same write (`terminal.go:45`), so a terminal that ignores OSC 11 still answers and pop learns "no" in one round-trip rather than at a timeout. No answer, an error, or a terminal pop does not hold the foreground of, resolves to **plain**.
- **Mode 2031 is the doorbell, never the answer.** A colour-scheme notification reports the *operating system's* setting, which is not the terminal's background — a light OS with a pinned dark terminal would report light. So a notification only triggers a re-query of OSC 11. Measured: enabling mode 2031 in a tmux pane, flipping the OS appearance and flipping it back delivers `ESC[?997;1n` then `ESC[?997;2n`; `ultraviolet` decodes those into `DarkColorSchemeEvent`/`LightColorSchemeEvent` (`decoder.go:432`), and although bubbletea v2.0.0 has no case for them, `translateInputEvent` ends in `return e`, so they reach a model unchanged.
- **`ui.RunProgram` is the one chokepoint.** It enables mode 2031, resolves the initial appearance before the program takes stdin, wraps the caller's model in a thin outer model that intercepts `tea.BackgroundColorMsg` and the two colour-scheme events (re-requesting the background colour on a notification), unwraps the inner model on return, and disables the mode. All ten `tea.NewProgram` sites run through it, so a picker and the Work dashboard cannot disagree about the palette.
- **Styles read the appearance, they never capture it.** The pinned colours in `ui/util.go` become `lipgloss.LightDark` pairs reached through accessor functions, with today's value as each dark member. Package-level style *vars* are the same bug in another hat: a value captured once from a fact that changes.
- **A cached rendering keys on the appearance.** The Document peek already re-renders when its width changes; the appearance is a second key on that same cache, so nothing in the dashboard handles an appearance message at all.
- **The one-shot query is guarded.** The non-TUI path checks `tty.ForegroundPgrp` and runs inside `tty.GuardRead`. Raw mode from a background process group raises SIGTTOU, whose default action stops the whole group, and pop runs its own commands in panes.

## Considered options

- **Keep `WithAutoStyle` and fix termenv** — rejected. The refusal is a hardcoded `TERM` prefix test in a dependency; carrying a fork or a patch to restore a query pop can make directly is a permanent cost for a one-line call.
- **Drop the pinned 256-colour values for ANSI indices 0–15** — considered seriously and rejected. The terminal's own theme defines those in both variants, which is why the rest of pop already looks right, and it would remove the need for the fact in the styling half entirely. Two roles collide: `colorDim` (241) and `colorSeparator` (238) both want "less contrast than body text" in different amounts and ANSI offers only `8`, and the warning orange (214) would land on the same `11` as the working spinner, collapsing "warning" into "an agent is live". Mixing the two systems in one palette was rejected in turn as the version that teaches the next reader the wrong rule.
- **Treat a 2031 notification as the answer** — rejected; see above. It is the same class of bug as the one being fixed: a confident answer to a question that was not asked.
- **An exported `SetAppearance` each model calls** — rejected. Nine surfaces to remember and one to forget, and the one that forgets holds a stale palette with no symptom but the wrong colour.
- **An override — `POP_APPEARANCE`, `GLAMOUR_STYLE`, or a config key** — offered and declined. The Override config layer is the wrong home outright: it is keyed by repository and would follow a human into a terminal it was never written for. Nothing else is needed while detection works, and the fallback is legible.
- **Polling the background colour on the dashboard's existing 2s tick** — dropped once mode 2031 measured working. A push that fires on a theme switch beats a query that fires 1,800 times an hour.
- **A `make live-appearance` target** — dropped as unearned. It would re-run this session's probes by hand, and its failure mode is "your terminal did not answer", which is not pop's regression to catch.

## Consequences

- **Plain is a real member of the appearance, not a defensive default.** glamour v1.0.0 hardcodes `ColorProfile: termenv.TrueColor` (`glamour.go:83`), so an explicit dark or light style emits ANSI even into a pipe. Only the no-TTY style keeps a redirected `pop tasks artifacts --show` byte-exact, which ADR-0222 requires.
- **Do not use `lipgloss.HasDarkBackground`.** It returns `true` — dark — on error (`query.go:79`). Pop calls `BackgroundColor` and maps an error to plain, or "silently assume dark" comes back one layer up.
- **The fix degrades in tiers, and the worst tier is better than today.** No OSC 11 answer means plain, legible on any background. No mode 2031 support means no liveness, which is where pop stands today. `screen` forwards neither and lands on plain — the case termenv's refusal was actually written for. Nothing here reads an operating-system setting, so nothing here is macOS-specific.
- **A `SIGKILL`ed pop leaves mode 2031 enabled**, and the terminal then sends `ESC[?997;2n` to whatever runs next, which a shell prints as noise on the following theme switch. Accepted: any program that sets a terminal mode carries this, bubbletea's own alt screen and mouse reporting included.
- **Dark users see no change at all.** Every current colour is its own pair's dark member.
- Glossary: **Terminal appearance** is added, and **Document peek** is redefined to say which palette it renders in.
