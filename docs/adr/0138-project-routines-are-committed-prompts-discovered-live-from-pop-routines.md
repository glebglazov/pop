# Project routines are committed prompts discovered live from .pop/routines

A repo can now ship routines to everyone who works on it: each committed `.pop/routines/<name>.md` is a **Project routine** — filename is the name (authored-id validation rules; an invalid or unparseable file is warned about and skipped, never fatal), body is the prompt, optional YAML frontmatter carries `agents` and `effort` only. Discovery is **virtual**: pop reads the checkout's `.pop/routines/` live at list/fire time, the file is the sole source of truth, and nothing is ever copied into the data-dir `routines/` registry — so the Queue daemon, whose discovery registry that directory is (ADR-0119), never sees Project routines at all. The materialized alternative (auto-syncing files into the registry) was rejected: it needs reconcile-on-change/delete machinery and creates drift between two copies for no benefit.

Project routines are **manual-fire only, by design and not merely by default**: a shared routine firing on a shared schedule is usually senseless (if everyone's daemon ran the same NewRelic-bugs research in the same repo, the runs would be redundant), so a `schedule` frontmatter key — like any unknown key — is warned about and ignored, and schedule-edit surfaces reject Project routines outright. With no daemon fire path, the created-paused/anchor ceremony (ADR-0124) and the pause bit itself don't apply: a Project routine has no pause state, and the CLI list renders `-` in the pause column.

The sharing boundary is: **definition via git, state per user per checkout.** A fire runs in the checkout it was triggered from, with the standard run wrapper and completion-sentinel contract. Run rows, Routine memory, and reports live in pop's data dir under a separate `project-routines/<checkout-key>/<name>/` root (never under `routines/`), and run rows key on the canonical checkout path + name — so sibling worktrees and teammates share the prompt but never share memory, history, or exclusivity. A deleted or renamed prompt file simply vanishes from surfaces; orphaned per-checkout state is tolerated as garbage.

Addressing and editing: an authored Routine id wins an exact-name match on the CLI, with `project:<name>` as the explicit form (and the escape hatch when shadowed). Surfaces list a checkout's Project routines only when invoked from inside it, visually marked as project-origin. Pop may edit the prompt file — including the agent-assisted refinement loop — but never commits the change; if the user likes the result, committing is their act.
