# Objective gates run in the drain, held as an executable convention kind

Pop never ran a project's build, test or lint command in the Task-set pipeline. The only facts about the work that pop read for itself were git's; everything else was a self-report: the Builder ticks its own acceptance boxes, the **Verifier** finds, runs and reports the gates itself, and the Refiner claims the gate it says it ran. The decision is to let pop run a repository's **Objective gates** and read their exit status, while the Verifier keeps what only judgment answers. The research behind it is `docs/research/2026-09-22-deterministic-gates-handoff.md`.

The decision, in eleven parts:

1. **The Gate manifest is a convention kind, `gates`, with a third Shape: executable.** Code parses it and no prompt carries it. The rejected homes were a config leaf and a standalone file. Config's `[work]` table is global-only, and `[repo."<path>"]` holds facts about a checkout, not commands. A convention already resolves per repository through ranks and has get/set tooling. The file is TOML (`gates.toml`, through a per-kind extension), because humans edit it and need comments. The kind has no Overlay layers, because a list of commands cannot be appended to as prose can. It is writable at project and repository rank only: a command is a fact about one repository, so a global answer would be wrong for every repository but one.

2. **A manifest at a rank is the switch.** The shipped rank answers "no gates", so a repository with no manifest runs exactly as before, and an upgrade turns nothing on. A global `[work.gates].enabled` (default true) is the kill switch. The project rank lets one human opt in on any repository without committing to its tree. That is how the new way is tested before it reaches other users.

3. **A result has three values: passed, failed, could not run.** Could not run never fails work. The gate goes to the Verifier marked "not run", and the Verifier checks that gate the old way. A malformed manifest counts as could not run for every gate. A gate that exceeds its `timeout` counts as could not run, not as failed.

4. **A gate declares where it runs, not what it is.** `at` is required and names one or more of four run points: `attempt` (after an implement attempt says complete, before pop commits), `refine` (before and after a Refine pass), `quiescence` (before the Verifier), `fold` (at the Fold landing gate). At each point pop runs every gate that names it, in manifest order. The handoff's `role` field (build, test, lint) is rejected: the point decides what a red result does, so a role would decide nothing. Pop stops at the first red result at `attempt` and `refine`, where the outcome is already decided, and runs every gate at `quiescence` and `fold`, where a reader needs all of them.

5. **No scoping.** A gate is a fixed command. Pop does not choose tests from a diff: that is judgment about one repository, and judgment is what this decision takes out of the gates. The Builder still runs related tests while it works, as before. A slow suite belongs at `quiescence`, not at `attempt`.

6. **A red result goes to the role that owns the moment.** At `attempt`, the attempt fails as a contract fault, the output goes into the ADR-0040 digest, and the attempt spends a try under the single budget of ADR-0231. At `refine`, red before the pass is `gate-blocked` and red after it is `abandoned`; pop measures both instead of trusting the Refiner. At `quiescence`, the Verifier is still called, with the results as evidence, and code refuses PASS while any gate is red. The rejected alternative skipped the Verifier and stored a FIXABLE verdict written by the gate. That would turn a disagreement between spec and test into an automatic Remediation task that cannot resolve it, the same trap ADR-0276 closes for Intent drift.

7. **Gate services are started probe-first.** A manifest declares services with `up`, `ready` and an optional `down`, and each gate lists what it `needs`. Pop probes first. A service that is already ready is neither started nor stopped, so pop never stops infrastructure a human or another drain is using. A service pop started is stopped at drain end. `up` must return once the service is started. A service that cannot be made ready makes every gate that needs it could not run, and a red gate whose service fails a probe run afterwards is reclassified the same way. A manifest-level `wrap` goes in front of every command, because environments come from tools such as direnv and mise that a plain `sh -c` does not load. Keeping parallel checkouts from colliding on shared infrastructure is the repository's job, not pop's.

8. **A gate that was red before the work is found out lazily.** When a gate is red, pop runs that one gate once at the commit before the work, in a scratch worktree, and caches the answer by SHA. Red there too means the gate is advisory for this set and is reported as a Severe journal event. The rejected alternative ran a baseline at every drain start, which costs a full suite every time on a large repository.

9. **Verdicts record their author and the manifest they saw.** `verify_verdicts` gains `source` (`agent`, `human`, `gate`, `range`) and a Gate manifest fingerprint. A cached verdict is reused only while the fingerprint matches, so turning gates on or off re-verifies once. Gate results are keyed by work SHA, gate and fingerprint, so a run at an unchanged tree is reused, not run again.

10. **An agent writes the manifest, and a deterministic dry run proves it.** `pop conventions assist <kind>` is an attended session that drafts any convention kind at a chosen rank. For `gates` it ends by running `pop gates check`, which runs every service and gate once at HEAD and prints the three-way results. Runtime verbs live under `pop gates`, not `pop conventions`, because no other kind can use them. The rejected alternative was a deterministic probe that drafts the manifest. Real repositories need judgment to write one: foreground service scripts, an environment loaded by direnv, services shared across checkouts.

11. **Every gate run is recorded, and the Verifier gets pointers, not logs.** Each run, whatever its result and whatever the point, writes one `gate_results` row and one log file under `<set>/gates/`. The file keeps its first ~256 KB and its last ~4 MB. The Verifier receives each `quiescence` result with its log path, the last ~100 lines of each red or could-not-run log, and one line for each earlier red run in the set. The history is kept because a gate that went red and then green on a diff that removed a test is the signal of weakened tests. Pop does not extract failure lines: which lines are the failure differs by ecosystem, and the Verifier searches the full log itself. Humans reach the logs through `pop gates show <set>` and through a pointer on the detail view and the Assist prompt.

## Consequences

- This amends [ADR-0227](0227-a-role-driving-convention-is-the-prompt-body-pop-owns-only-the-frame.md): a kind may now have a Shape that is never a prompt. When gates exist, pop selects a second, judgment-only shipped `verification` body. A body a team wrote at a higher rank is left as written, even if it tells the Verifier to run the gates again, so there is still one voice on what to check.
- **Objective gate** widens from the Eval harness of [ADR-0268](0268-the-eval-harness-compares-a-bare-agent-with-pop-on-spend-and-graded-quality.md) to all of pop. The Eval runner moves into a leaf package below `tasks`, shared by both, and gains the third result value it lacked.
- The rollout is measured, not judged by feel. A new Eval Arm, Pop with Objective gates, runs beside the Pop Arm. The Pop Arm's isolated config turns the kill switch off. The gates Arm commits the Case's `gates.toml` at repository rank before the Trial starts, so it is not graded as part of the diff. The harness refuses the gates Arm when a project-rank or global-rank manifest on the machine would override the Case's.
- `REFINE-OUTCOME` now fails closed to `abandoned`, and agent commit subjects are checked against a Conventional Commits `commits` convention. Both ship to every user with no switch. A Refiner that always leaves out the outcome line refines again on each drain.
