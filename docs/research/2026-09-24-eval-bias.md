# Eval bias and representativeness review

Date: 2026-09-24. Scope: the Eval harness in `eval/` at `188a607` and the first
Matrix (4 Cases × Bare and Pop × repeat 1, results in `eval/results/`). This review comes from code reading and from a search of the saved
Trial evidence. No new Trial or Grader run was made for it.

## Result

The Eval is not yet representative or free of bias. The Reference check (in
work) removes one source of bias: Acceptance items that the Grader cannot read
correctly. The problems below are still open. They are listed with the
largest first.

## Findings

### 1. One repeat per cell

Each Case × Arm has one Trial. A gap such as `drain-rendering` Bare 0.778 and
Pop 0.611 is within normal run-to-run variation. With one repeat, the rollup's
spread columns are all zero, so they tell nothing. No comparison between Arms
is supported until each cell has at least 3 repeats.

### 2. The Cases favour Pop by selection

All four Cases come from historical Pop Task sets in this repository
(`go run ./eval prepare <repo> <set-id>`). This has two effects:

- The Pop arm gets the historical task split. The Bare arm gets the same words
  joined into one `spec.md` and must plan by itself. `eval/README.md` records
  this planning asymmetry.
- The Cases are work that Pop already finished well enough to land. Work that
  Pop did badly, or never took, is not in the corpus.

The fix needs Cases that did not come from Pop, for example changes that a
human wrote.

### 3. Fitting the list to the Reference adds a bias

The Reference diff is the final historical Pop result, including its
Remediation commits. Where the spec says nothing, fitting the Acceptance list
to the Reference moves the list toward what that Pop run did. Rule: fix each
item against the spec, and use the Reference only to find where the list is
ambiguous. When the spec and the Reference disagree, the spec wins, and the
item is kept with an accepted reason.

### 4. The Grader sees the list only

`graderPrompt` (`eval/grade.go`) gives the Grader the Acceptance list, the
quoted standards, the scope flag and the diff. It does not give it `spec.md`.
So an item must be correct without the spec. In `drain-rendering`, the spec
limits Task result lines to "a whole-set drain" (`spec.md:43`), and items 7, 9
and 10–13 do not. The Grader applied them to single-task runs as well. That
gave Pop 11/18 and Bare 14/18. Read against the spec and the Reference, both
Arms are about 16/18 (from code reading, not a Grader run). The Reference
itself fails items 6, 7, 9 and 10–13 under the Grader's reading.

### 5. Grader noise is not measured

One Grader model (`eval/graders/grader.toml`, Codex `gpt-6-astra`) grades each
Trial once. When the Grader changed from `gpt-5.5` to `gpt-6-astra`, the same
Trial got a different verdict on one item. The item-level agreement between
two grades of the same Trial is unknown. A cheap measure: grade the same
Trials 2–3 times and record how often each item agrees. That gives the size a
score gap must have before it means something. A judge panel was rejected as a
fix for ambiguity. Its disagreement is still useful as a signal that an item
is ambiguous.

A first measure came from the regrade after the Reference check. The same
Grader (`gpt-6-astra`) graded 6 Trials a second time against a list that had
not changed (`detail-keymap`, `work-lift`, and `verify-report` without item 2).
The item verdicts agreed on 147 of 148 items (99.3%). The one change was
`verify-report` Bare item 4, from not met to met. The quality score changed in
2 of 6 Trials, by one point each (`detail-keymap` Bare 4 to 3, `verify-report`
Bare 3 to 4). In the `verify-report` Reference check, item 23 was met in one
run and not met in the next, with the same Reference and the same item text.
So one item verdict or one quality point can change between runs. A gap of
one item or one quality point between Arms does not mean something.

### 6. Possible answer leak through git history

`cloneAtCommit` (`eval/draft_acceptance.go`) makes a full clone and then
checks out the parent. The later commits stay in the Trial clone: the
Reference commits, and `eval/cases/*/acceptance.md` on `origin/master`. The
Bare prompt does not tell the agent to keep out of history.

A search of the saved evidence of all 8 Trials (Bare `capture/`, Pop
`reports/`) for the Reference end SHA, `git log --all`, `origin/master`,
`eval/cases` and `acceptance.md` found 0 matches. For Pop this check is only
partial: its full attempt streams are deleted with the Trial work directory.

The fix: the Trial clone holds only the parent commit, so no agent can read
the answer, whatever it does. The Grader clones and the Reference patch read
must keep the history that they need.

### 7. Smaller points

- The 1–5 quality scale is coarse, and one Grader run sets it.
- The Grader holds a Trial to `AGENTS.md` only (the thin Grader standard,
  accepted as it is).
- The corpus is small: 4 Cases, all Go, all in this repository.

## Recommended order

1. Finish the Reference check, with the rule in finding 3.
2. Make the Trial clone hold only the parent commit (finding 6).
3. Run at least 3 repeats per cell (finding 1). Grade each Trial more than
   once to measure Grader noise on more items (finding 5).
4. Add Cases that did not come from Pop (finding 2).
