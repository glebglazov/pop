1. The overall shape

Three processes, no messaging between them. The supervisor spawns a drain into a tmux pane and never hears from it again; coordination is entirely poll + pure read + diff over pop.db, the manifest files on disk, and tmux pane options.

gate holds, captured runs" --> DB L -- "task status transitions" --> MD L -- "topic, pane status" --> TM DB -- "polled" --> T MD -- "re-read" --> T DB -- "read" --> D MD -- "read" --> D style P2 stroke-width:3px
There is no event bus. The only genuine byte stream in the system is agent stdout, consumed inside one attempt. Everything called an "event" elsewhere — work.AdvanceEvent, streamEventRecord — is a record produced and consumed within a single call stack, never delivered to a subscriber.

Why dispatch is serial while reads fan out: dispatch mutates the shared checkout ledger, and "first wins, rest defer" needs a defined order. Reads observe nothing of each other.

Reconcile failure never fails the tick — that kind's candidates then read pre-reconcile state, no worse than before the phase existed. A candidate failure does fail it.

3. Layer 2 — the Implement run loop

cmd/tasks.go:1063 → implement.RunWholeSetWith → tasks.RunTaskSetWith (tasks/run_tasks.go:102)

run, err := newImplementRun(...)   // plan + paths + the opening BeginDrain
defer run.finalize(&err)           // registered right here, before BindCheckout
run.setup()
run.loop()

The deferred finalize sits at exactly that point so a failure in later setup — checkout bind, dirty check — still writes the Drain row's exit terminal. Failing at or before BeginDrain leaves no live Drain, so there is nothing to finalize.

The implementRun object

tasks/implement_run.go:26

One Implement run is the whole invocation; a Drain is the per-segment runtime execution lock it re-acquires. The name is deliberately neither "session" (a tmux word) nor "drain" (the store-row word). It carries the state the loop branches and the deferred finalize share:

FieldWhy it lives on the run, not in a loop local
drain *DrainHandlenil while parked at a gate or quota wait; finalize must read the latest value
sharedPromptReaderstdin cannot be re-wrapped per gate — one reader for every gate in the run
dirtyStrategyAppliedat most once per run; must survive the gate parks that re-enter the loop
agentProbeMemoone-way availability memo: a preset marked unavailable stays skipped for the whole process
resultaccumulates across iterations; read by finalize for the exit terminal

4. Drain segments and the runtime execution lock

tasks/implement_run.go:273 (parkDrain), :287 (parkAtGate), :329 (ensureDrain) — ADR-0067

One run holds at most one Drain and may span several. Every human-wait gate parks the lock, so the menu, the assist session and the runtime shell all run lock-free — otherwise a human staring at a prompt would hold a checkout hostage indefinitely.

The list of presets, the retry cap, and the tier are three different budgets, and the scope of a verdict picks which one is spent. That is the whole dispatch rule.

The probe is memoised one-way per process: probed at most once, and a preset marked unavailable stays skipped until the process ends. Only an explicit negative skips — a non-zero exit, unparseable output or a 5s timeout reads as unknown and proceeds, because a probe must never block real work on its own parse failure.

The verdict grid

Every adapter answers with one type, AgentProceedVerdict. Dispatch reads Scope × Recovery only; Kind is explicitly descriptive and picks human-facing wording, never a branch. That is what lets a new kind land without editing the orchestrator.

Recovery = timeRecovery = humanRecovery = permanent
Scope = preset write the machine-global preset cooldown, enter the quota recovery wait no cooldown; if every preset lands here, exit ExitSetup and leave the task Open no cooldown, no wait
Scope = model record a timed Effort model skip for (preset, model), restart on the tier's next entry record a permanent skip — zero Until, renders as ∞

A model-scoped verdict with no surviving tier entry escalateToPreset()s: same cause, same recovery, but condemning the whole preset so Agent fallback advances.

7. Layer 4 — one agent process

tasks/attempts.go:538 (runAgentAttempt), tasks/stream.go:164 (streamRecorder.Write)

This is the only concurrency in the whole drain process: one goroutine on proc.Wait() and a select over three channels.

sequenceDiagram autonumber participant EX as executeTaskAttempts participant RA as runAgentAttempt participant W as writer chain participant AG as agent CLI process participant FS as disk / pop.db EX->>RA: invocation RA->>FS: spillPrompt — prompt leaves argv
for this attempt only (execve ceiling) RA->>W: liveRenderWriter → streamRecorder → capture buffer RA->>AG: startAgentInvocation, own process group RA->>RA: signal.Notify before start —
a signal must never hit the default action loop while running AG-->>W: stdout bytes W->>W: split on newline, stamp AtMS,
append streamEventRecord W->>W: adapter Render(event) → live prose + tool ticks end Note over RA: select over sigCh / done / timeoutCh AG-->>RA: exit RA->>FS: cleanupPrompt (deferred) RA-->>EX: raw capture + outcome EX->>EX: NormalizeOutput(raw) — verdict scan over the WHOLE capture alt ProceedVerdict present EX->>FS: persist stream as quota-paused / agent-unusable else EX->>FS: re-read task .md EX->>EX: assessAttempt(output, exitCode, taskData) EX->>FS: persist stream (completed / failed) as JSONL.gz + Captured run row opt complete EX->>FS: completeSuccessfulTask — commit + transition write end end

Two ordering facts that are load-bearing:

  • Timestamps live at the bytes. streamRecorder stamps each line as it arrives, before any rendering, so a render bug or an unrecognised event type can never distort the persisted record (ADR-0016). Live rendering is cosmetic; the capture is the source of truth.
  • The verdict check precedes assessment. An agent that could not run is never graded as a failed attempt.

Plain-output and --agent-cmd attempts bypass both writers — io.MultiWriter(liveOut, &capture), no records, no adapter capabilities.

8. Seams: who declares, who implements

classDiagram class Kind { <> ID() KindID Load() []Container StatusCell(Container) Actions(Container) StatusActions(Container) ItemActions(Container, Item) Perform(Container, *Item, Verb) Columns() []string } class Advancer { <> Reconcile() error Candidates() []Candidate Advance(Candidate) Outcome } class SkipSource { <> ModelSkips() []ModelSkip } class AgentAdapter { <> HeadlessInvocation() NormalizeOutput() AvailabilityProbeCapability() EffortLadderCapability() plus 13 capability stances } Kind <|.. setkind : Task set Kind <|.. mapkind : Map Kind <|.. routinekind : Routine Advancer <|.. taskSetKind : embeds setkind Advancer <|.. routineAdvancer SkipSource <|.. setkind : Effort model skips
are machine-global AgentAdapter <|.. presetAgentAdapter : one struct,
data-configured per preset note for mapkind "implements Kind and NOT Advancer:
every Decision ticket needs a human session.
That asymmetry is what makes the split load-bearing."

The supervisor obtains an advancer by type-asserting a kind it already holds (work.Advancers), so a kind that cannot be advanced answers nothing and is never asked again. Same trick for SkipSource and for the consumer-side spawnedSetsReporter declared in supervisor.go:196 — which lets the supervisor ask for spawn seeding without naming the Task-set package.

work/ imports no kind and no TUI; two guard tests hold that. supervisor/ imports tasks/drain and nothing imports it back.

Agent capabilities are deliberately not Go interfaces. Each is a struct carrying a CapabilityKind stance — Supported (must carry the func) or Blind (must carry a reason) — validated at init, with the zero value capabilityUnset a hard error. A Go interface can only be satisfied or not; this makes "this adapter is blind to token usage, and here is why" a declarable, checked state.

9. What crosses a boundary

Nothing is pushed back to the daemon. The run writes, and other processes poll.

ChannelWritten byRead by
manifest .md files gates, completeSuccessfulTask, the transition.go chokepoint the run's own next RefreshWith; supervisor scan; dashboard
pop.db — drain rows, preset + model cooldowns, recovery waiters, gate holds, checkout claims, Captured runs, work container registry BeginDrain / Finish, verdict handling, walk.retire, waiter registration supervisor reconcile and occupancy; pop tasks agents; dashboard footer
tmux @pop_topic, @pop_work_kind, @pop_work_id, pane status PreSeedTopic; agent CLI hooks installed by integrate/ monitor/ pane daemon; the dashboard's pane handoff

The one genuine push channel anywhere in pop is the last row: agent CLI hooks fire into the monitor/ pane status daemon. Everything else is polled.
